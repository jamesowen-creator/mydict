## 작업 규칙 (프로젝트 지침 + 합의)
- Claude Code 지시와 결과 보고는 모두 **작업 번호를 붙인 블록**. 지시문은 복사해서 붙일 수 있게 **코드 블록 하나**로 쓴다. 사용자는 스크롤해서 이전 내용을 보지 않으므로 필요한 블록은 다시 보낸다.
- **작업 번호 체계(2026-10-19 정리, 작업 311)**: 앞으로의 작업은 접두사 없이 메인 번호 하나로 이어 가며 지시문을 낼 때마다 1씩 올린다(311이 이 문서 갱신 작업). 일본어 문법은 JG-1~JG-7, 개념학습 삭제는 CL-1로 당시 번호 그대로 기록하고 다시 매기지 않는다. 번호 없이 보고되었던 홈 휠 편입(4310ac6)은 작업 309, 읽어주기(d1d8319)는 작업 310으로 기록한다(푸시된 커밋 메시지에는 각각 "N"·"작업 번호 미정"으로 남아 있고 수정하지 않는다). 작가 노트는 AN-n(작가 노트 절).
- 말투는 존댓말. 문서는 간결·직관, **확인된 사실과 추정을 구분**(hallucination 경계).
- "매번 확인": 수정 전에 합의된 방향을 한 줄로 확인하고, 수정 후에는 합의 대비 달라진 점을 보고(Claude Code 보고의 [어긋남]).
- API 비용이 드는 작업은 **Haiku 먼저 제안**, Opus는 꼭 필요할 때만 물어보고. 비용 승인 없이 API 호출하지 않는다.
- **(2026-10-13~14 추가) 새 지시 블록은 결과 보고가 와서 검토된 뒤에만, 한 번에 하나씩 만든다.** 보충 블록을 여러 개 겹치지 않는다(사용자: "자꾸 꼬여"). 변형 확인은 블록에서 명시한 경우에만. 테스트는 관련 묶음만, 전체는 배치 끝에만(부하성 UI 실패는 해당 파일만 2회까지 재실행). 새 테스트는 t.after로 서버·페이지를 닫는다. 품질 판단은 나중에 사용자가 폰에서 한꺼번에. 모든 UI 작업은 디자인 원칙을 지킨다. 커밋 메시지 끝에 Co-Authored-By와 Claude-Session 두 줄. 자세한 내용은 claude/concept-map-progress-275.md 8절.
- 가벼운 절차: 관련 테스트만, 커밋 1개, 보고 15줄 이내. 첫 실행 실패가 있으면 푸시 보류 → 내용·의도 확인 후 승인(의도된 기대값 변경만 승인).
- 테스트: `node --test "tests/**/*.test.js"`, UI 테스트는 tests/ui/*. tests/legacy는 기본 실행에 포함됨(옛 회귀 8개를 run_all.test.js가 모의 DB·가짜 SDK로 실행, 외부 접근 없음, 약 10초, 유지 결정 235-3). Claude Code 임시폴더의 옛 테스트는 실행 금지.
- 공용 파일 수정 금지(계획된 경우만): public/css/common/*, public/js/common/*, sw.js, home, admin, server.js, routes, lib. 프로세스 종료는 본인 PID만. **운영 DB는 Claude Code가 접근하지 않는다.** DB·서비스 삭제는 백업과 항목별 사용자 동의가 있어야 한다.
- 사용자는 Railway에서 SQL 직접 입력을 부담스러워한다 → 요청하지 않는다. 눈으로 보는 확인 또는 Claude Code 읽기 전용 확인을 우선.
- claude/* 문서는 프로젝트 지식(오케스트레이터가 직접 갱신)과 저장소의 markdown_20261010\claude\ 사본(Claude Code가 갱신)에 둔다. **사용자는 파일을 직접 옮기거나 복사하지 않는다(사용자 결정 2026-10-10).** 문서를 바꿀 때는 지시문 안에 내용(전체 또는 교체할 부분)을 넣어 Claude Code가 폴더에서 직접 만들거나 수정하게 한다. Claude Code는 프로젝트 지식을 읽을 수 없으므로 필요한 내용은 지시문에 담는다. **문서 갱신은 작업 몇 개를 마친 뒤 가끔 한꺼번에 한다(사용자 결정 2026-10-10).** 갱신할 때는 프로젝트 지식과 저장소 사본을 같은 턴에 맞춘다.

## 보안 규칙
- API 키·DB 연결 문자열은 채팅과 Claude Code에 **절대 붙여넣지 않는다.** 실험 키는 사용자가 PowerShell Read-Host(보안 입력)로만 입력(프로세스 환경변수, 종료 시 삭제).
- 비밀이 들어 있을 수 있는 파일(.env 등)을 검토해 달라고 하면 먼저 경고. keys\(정답표) 폴더는 판정 전에는 열지 않는다.
- Railway 변수 값은 열람·기록하지 않는다. **jamesowen API 키는 앱이 쓰므로 삭제 금지.**

- 수록·검증 규칙(scripts/validate_artist_notes.js가 검사하는 것):
  - 고인만 수록(death_year 정수, birth_year보다 큼, alive 등 필드 금지). 원문·미디어 필드 금지(full_text, lyrics, lyric, text_original, original_text, score, image, images, audio). 내용은 패러프레이즈만.
  - featured_works 2~3개. other_works는 배열이면 되고 개수 제한은 없음(작성 권장은 3~5개). note는 40자 이하.
  - 카드 본문 400자 이하: who, life, movement.text, 대표작 1건(description+interpretation), reputation(당대+후대 합산), summary. 문단 구분 줄바꿈은 글자 수에 넣지 않음.
  - name·full_name 필수, movement.tags는 비어 있지 않은 문자열 배열.
  - connected_artists 0~3명, reason 40자 이하, id는 null 또는 수록 작가 id.
  - checked·sources는 비어 있으면 "미검증"으로 허용하고 값이 있을 때만 형식(날짜, http(s) URL) 검사. 실행 결과에 미검증 작가 수를 출력.
  - 퀴즈(quiz[], AN-2): id 중복 금지, type은 mcq|ox, artist_id는 실제 작가, verified_on은 YYYY-MM-DD 날짜, basis[] 필수. 4지선다는 question·options 4개(정규화 후 서로 다르고 모두 실제 작가 name)·answer(보기 중 정확히 1개, artist_id 작가의 name)이고 statement·explanation 금지. OX는 statement·answer(boolean)·explanation 필수, claim_tag가 있으면 answer가 그 작가 movement.tags 포함 여부와 일치, options·question 금지. basis[]의 각 항목(artist_id, path, equals 또는 includes 중 하나)은 현재 JSON에서 풀리고 값이 일치해야 한다(정답과 데이터가 어긋나면 오류). 글자 수 상한은 문항·진술 60자, 보기 20자, 해설 120자. 원문·미디어 금지 필드는 문항에도 적용.
- **checked·sources는 "출처를 단 날짜와 URL"이며, 내용 검증을 마쳤다는 뜻이 아니다.** 내용 검증은 136-a~136-b(1차)와 AN-3(2차)로 했고, 현황은 아래 "내용 검증" 절에 있다. 2차 대조에서는 checked·sources를 갱신하지 않았다.
- 연결 작가 규칙: 같은 예술 사조(movement.tags가 하나 이상 겹침)일 때만 연결하고 시대·교류·헌정·가족 등 다른 배경으로는 잇지 않는다. 0명이면 "연결 작가" 카드를 숨긴다. 수록 작가끼리는 양방향으로 맞춘다(검증: id가 있는 연결은 태그 겹침이 없으면 오류, 양방향이 아니면 경고만). 수록 외 작가는 웹 검색으로 같은 사조임을 확인한 경우에만 쓰고 id는 null. AN-5 이후에는 연결이 0명인 작가가 없다(김환기는 유영국과 연결). 화면은 연결 작가의 링크 텍스트를 connected_artists[].name에서 그대로 가져오므로(id로 이름을 조회하지 않음) name은 대상 작가의 통용명과 같게 쓴다(AN-6에서 10곳 통일).

### 퀴즈 구조 (AN-2, public/artist_notes_db.json의 quiz[])
- 문항 42개: 4지선다(mcq) 12, OX 30(O 15 / X 15). 작가별 7개씩(artist_001~006), 새 6명(artist_007~012)은 0개(AN-5에서 문항을 추가하지 않음). OX 중 claim_tag 있는 것은 4개.
- 문항 필드: id, type(mcq|ox), artist_id, basis[], verified_on(현재 모두 2026-10-18). mcq는 question, options[4], answer(작가 name). ox는 statement, answer(boolean), explanation, 선택 claim_tag.
- 근거 참조(basis)는 데이터와 검증 스크립트(scripts/validate_artist_notes.js, `npm run validate:artist_notes`)에서만 쓰고 화면에는 표시하지 않는다. 검증 규칙은 위 "수록·검증 규칙"의 퀴즈 항목, 화면 동작은 "화면과 동작"의 퀴즈 탭 항목에 있다.
- 문항 내용은 현재 본문 데이터와 basis로 연결되어 있어, 본문을 고치면 검증 스크립트가 어긋난 문항을 오류로 알려 준다.
- 문항 없는 작가의 처리 [확인함: 코드 읽기와 AN-5 화면 확인]: 새 6명만 정복하면 출제할 문항이 0개라 안내창("퀴즈를 생성할 수 없습니다. 더 많은 작가를 정복해보세요!")만 뜨고 시작하지 않는다. 기존 작가와 섞어 정복하면 기존 작가 문항만 출제된다. 검증 스크립트는 작가마다 문항을 요구하지 않는다.

### 내용 검증 (136-a~AN-5)
**검증 기준(실제로 적용한 것)**
- 사실 1건당 독립 출처 2개 이상, 그중 1개 이상은 비위키로 하고, 본문을 열람해야 "일치"로 본다. 위키백과 계열 문서는 여러 개라도 독립 출처 1개로 센다.
- 비위키로 인정하는 것: 브리태니커, 미술관·재단·공식 기관, 악보 출판사, 학술·전문 출판물. 인정하지 않는 것: 여행 정보 사이트, 검색 결과 요약만 본 것, 개인 블로그, 출처 없는 요약 사이트.
- 김환기는 한국어 1차 출처(환기미술관, 국립현대미술관 등)를 우선하고, 구하지 못하고 한국어 뉴스·잡지만 일치하면 "보조 확인"으로 표기한다.
- 판정 종류: 일치 / 보조 확인 / 수정 필요 / 근거 없음 / 검증 불가(위키만 일치) / 검증 불가(미확인).
- 확인하지 못한 문장은 삭제를 우선하고, 평가 문장은 출처 있는 평가만 남긴다. 검증 보고서에는 출처 URL을 적지 않는다.
- 문장 ID 형식: 작가코드-필드-순번. BTH 베토벤, GOG 고흐, MON 모네, KHK 김환기, MOZ 모차르트, CHO 쇼팽. 필드는 oneline, who, life, movement, featured1/2-desc·interp, rep-contemporary·rep-posthumous, summary. other_works는 작가코드-OW-순번. 문단 구분("\n\n")은 문장 경계로 보고, 괄호·「」 안 마침표와 라틴 약어(E. T. A., K. 550, Op. 23)는 자르지 않는다.

**현황(AN-3 적용 후)**
- 6명의 본문 문장(144문장)과 "그 밖의 작품"(25건)을 대조 완료했다. 수정은 1차 47건(136-b: 교체 44, 삭제 3)과 2차 21건(AN-3), 그 밖에 137·AN-2의 데이터 수정이 있다. 2차 대조는 별도 세션에서 검색 결과의 본문 발췌 기준으로 했고 전문 열람은 아니다. 이 세션에서는 확인하지 못했다. 브리태니커 일부 페이지 등 차단된 출처는 1차 때 이 작업 환경에서 열리지 않았다(NGA, MoMA, 시카고미술관, 환기미술관, 국립국어원 포함).
- 단일 출처로 남은 항목: MOZ-life-3(오스트리아 미디어테크 1곳), MON-featured1-desc-2(블로그 1곳).
- 보조 일치로 유지한 항목: CHO-OW-3(악보 판매처·교육 사이트), MON-OW-1(소장 기관 해설 1곳), KHK-featured1-interp-1(한국어 매체).
- 김환기 항목은 한국어 1차 출처(환기미술관, 국립현대미술관)를 이 환경에서 열지 못했고 한국어 매체·공공기관·소장 기관 서술로 확인했다.
- 위 기준(사실 1건당 독립 출처 2개 이상, 비위키 1개 이상, 위키 계열 1개 계산, 확인 못 한 문장은 삭제·완화)은 2차에도 그대로 적용했다. 위키백과 계열만 근거인 문장은 남기지 않았다.
- checked·sources는 "출처를 단 날짜와 URL"이며 이번 2차 대조에서 갱신하지 않았다(값은 2026-10-17~18 날짜와 작가별 6~12개 URL 그대로).
- 한국어 고유명사 표기는 국립국어원 용례를 열지 못해 추정 표기로 남은 것이 있다.

**신규 6명 검증 현황(AN-5)**
- 하이든, 슈만, 리스트, 르누아르, 고갱, 유영국은 별도 대화 세션에서 검색 결과의 본문 발췌 기준으로 사실 대조를 마친 확정표(생몰, 사조·tags, 카드별 허용 사실, 금지 사실) 안의 사실만으로 썼다. 전문 열람은 아니며 이 세션에서는 확인하지 못했다. 근거 기준은 위와 같다. checked는 2026-10-18, sources는 확정표의 URL.
- 단일 출처·보조 일치 항목:

  - 리스트 featured1 interpretation: 브렌델의 평(단일: 인터루드).
  - 르누아르 featured1 interpretation: 졸라 등 당대 비평가의 호평(단일: 라루스).

  - 기존 단일 출처 2건(MOZ-life-3, MON-featured1-desc-2)과 보조 일치 3건(CHO-OW-3, MON-OW-1, KHK-featured1-interp-1)은 그대로 유지.

### 화면과 API
- 화면: public/jgrammar.html(입력창 → [문법 설명], 사진 찍기·선택, 결과, 저장한 문장). API 4개(모두 로그인 + 일본어 문법 권한 필요):
  - POST /api/jgrammar/explain: 문장 분석(캐시 → 한도 → AI 순서, 권한 검사가 맨 앞).
  - POST /api/jgrammar/ocr: 사진에서 일본어 문장 인식.
  - GET /api/jgrammar/saved: 본인 저장 목록(최신 사용순). DELETE /api/jgrammar/saved/:id: 본인 항목 삭제, 타인·없는 항목은 404.
- 분석 응답 검증 상한(lib/jgrammar.js): 번역 200자, 문법 이름 60, 의미 200, 형태 120, 유사 표현 차이 300, 항목 최대 8개, JLPT는 N5~N1 또는 null. max_tokens 3000(분석), 2000(OCR). 검증 상한과 max_tokens의 적합성은 실제 응답으로 확인하지 않았다 [미확인].
- 하루 호출 한도: 기본 60회(환경변수 JGRAMMAR_DAILY_CAP, 허용 1~10000), 문법 분석과 사진 인식을 합산하고 캐시 적중·저장 목록 열람·삭제는 세지 않는다. 한도에 닿으면 429. 사용량은 api_usage에 이벤트명 jgrammar(분석)·jgrammar_ocr(인식)로 기록, 재시도로 호출이 늘면 그만큼 기록된다.

### DB
- jgrammar_cache: sentence_hash(앞뒤 공백을 뺀 문장의 sha256, 기본 키), sentence, result JSONB, model, created_at. 사용자와 무관한 공용 캐시. 단계 jgrammar_cache.
- users.perm_jgrammar: BOOLEAN NOT NULL DEFAULT false(기존 사용자도 모두 차단으로 시작). 단계 jgrammar_user_permission.
- jgrammar_saved(JG-6): user_id(users 참조, 사용자 삭제 시 연쇄 삭제), sentence_hash, sentence, result JSONB, created_at, last_used_at. (user_id, sentence_hash) 유일, 인덱스 (user_id, last_used_at DESC). 단계 jgrammar_saved.
- 세 단계 모두 IF NOT EXISTS라 여러 번 실행해도 안전하다. 실제 PostgreSQL에서의 생성·UPSERT는 확인하지 않았다 [미확인: 로컬 PG 없음].

### 권한 (JG-2)
- 서버: 관리자(ADMIN_EMAILS 또는 DB role=admin)는 항상 허용. 그 밖에는 perm_jgrammar가 명시적으로 true이고 차단 계정이 아닐 때만 허용. 사용자 행이 없거나 DB 오류·DB 없음이면 403(fail-closed). 이 검사는 캐시 조회·AI 호출·한도 계산·저장 목록 조회보다 앞이다.
- 화면: /api/me의 perm_jgrammar가 true이거나 role=admin일 때만 입력창을 보이고, 아니면 "사용 권한이 없습니다. 관리자에게 문의해 주세요."만 표시한다. 관리자 화면 "일본어 문법" 열은 "개념 지도" 열 오른쪽(권한 구조는 admin-permissions-243.md).

### 사진 입력 (JG-3)
- 앱의 기존 OCR은 영어 전용 클라이언트 Tesseract.js(사전 화면의 라이브 카메라)라 일본어에 쓸 수 없어 재사용하지 않고, 이미지를 Haiku에 직접 보내 일본어 문장을 읽게 했다. 업로드 방식(원본 바이너리 + 라우트 단위 용량 제한 + 형식 허용 목록)은 개념학습 음성 변환 라우트의 패턴을 따랐다.
- 이미지는 서버에 저장하지 않는다. 형식 JPEG·PNG·WebP·GIF(파일 서명 검사), 5MB 이하(기존 OCR에 상한이 없어 지시의 기본값), 화면에서 올리기 전에 긴 변 1600px의 JPEG로 줄인다. 인식 문장은 최대 30개, 응답 형식이 틀리면 1회 재시도. 인식 결과는 캐시·저장하지 않는다.
- 인식 결과로 바로 분석하지 않는다: 1개면 입력창에 채우고 여러 개면 하나를 탭해 고른 뒤, 사용자가 확인·수정하고 [문법 설명]을 누른다. 한도는 분석과 합산(이벤트 jgrammar_ocr).

### 저장 목록 (JG-6)
- 설명이 정상 반환되면(새 생성·캐시 적중 모두) 본인 목록에 자동 저장한다. 같은 문장은 1건만 유지하고 last_used_at만 갱신하며(결과는 바꾸지 않음), 사용자당 100건을 넘으면 last_used_at이 가장 오래된 것부터 지운다. 저장 항목을 열 때는 AI를 호출하지 않고 하루 한도에도 넣지 않으며 last_used_at도 갱신하지 않는다.
- 저장 오류가 나도 설명 결과는 정상 반환하고 로그에는 오류 코드만 남긴다(문장·결과 비기록). OCR 이미지와 인식된 전체 문장 목록은 저장하지 않는다. 이메일로만 관리자인 계정(users 행이 없음)은 FK 때문에 저장되지 않는다 [확인함: 시험].
- 관리자 화면에 저장 목록 열람 기능은 없다.

### 후리가나 (JG-7)
- 분석 응답에 ruby(입력 문장을 앞에서부터 나눈 {text, reading} 조각 배열) 추가. 서버 검증: 조각을 이어 붙인 값이 입력 문장과 정확히 같고, reading은 히라가나·ー만 30자 이하이며 한자가 있는 조각에만 있고, 조각 100개 이하. 검증 실패·응답에 ruby 없음이면 재시도 없이 ruby만 null로 두고 나머지 설명은 정상 처리한다. 한자가 없는 문장은 ruby가 빈 배열이고 읽기를 요청하지 않는다.
- ruby 키가 없는 옛 캐시는 한자가 있는 문장이면 처음 다시 요청될 때 AI를 1회 재호출해 새 형식으로 갱신한다(하루 한도 포함, 재시도 없음, 실패하면 옛 결과 반환). 저장 목록의 옛 형식 항목도 새 결과로 갱신된다(JG-6의 "결과를 바꾸지 않는다"에 대한 유일한 예외). 저장 항목을 열 때는 AI를 호출하지 않는다.
- 화면: 결과 맨 위에 원문을 후리가나(<ruby>)와 함께 표시하고 "후리가나 끄기/켜기" 링크(기억은 localStorage, 저장이 안 돼도 동작). 문법 항목 안의 일본어에는 붙이지 않는다. 안내문은 "AI가 생성한 설명과 읽기라 틀릴 수 있습니다".
- max_tokens 1800 → 3000(근거는 Claude Code의 계산이며 실제 응답 길이는 측정하지 않았다 [미확인]). 옛 캐시 재호출은 문장당 한 번씩 추가 호출이 생길 수 있어 비용이 늘 수 있다(규모는 모름).

### 홈 휠 (작업 309)
- 휠 항목은 기본 6개(언어 사전, 문학 나침반, 한입 독서, 과학, 음성 학습, 작가 노트) + (perm_jgrammar가 true이거나 관리자) 일본어 문법(언어 사전 바로 다음, 같은 언어 계열이라 선택) + (perm_concept_map이 true) 개념 지도(맨 끝)를 buildOptions로 조립한다. 보이는 항목 수는 6·7·8개 조합이 있고 어느 조합이든 가운데 카드 위 2개·아래 2개가 보인다. 개념 지도는 관리자라도 perm_concept_map이 꺼져 있으면 보이지 않는다(일본어 문법은 관리자가 항상 본다).

### 읽어주기 (작업 310)
- 결과 상단 원문 근처에 "듣기"(rate 1.0)·"천천히"(rate 0.7) 링크. 브라우저 내장 음성(speechSynthesis)만 쓰며 서버 호출·외부 음성 API·DB 변경이 없고 읽을 텍스트를 서버로 보내지 않는다. 사용자가 링크를 눌렀을 때만 읽는다(자동 재생 없음).
- 읽을 텍스트: ruby가 유효하면 reading이 있는 조각은 reading으로, 없는 조각은 text로 이어 붙인 것, 아니면 원문 그대로(후리가나 끄기/켜기와 무관). 저장 목록에서 연 항목도 같다. 문법 항목 안의 일본어는 읽지 않는다.
- lang ja-JP, 일본어(ja로 시작) 음성 우선(ja-JP 먼저), voiceschanged 처리. 읽는 중 링크 글자는 "멈춤", 같은 링크를 다시 누르면 중지, 다른 링크를 누르면 교체. 일본어 음성이 없는 기기에서는 "이 기기에서는 일본어 음성을 지원하지 않습니다" 안내, speechSynthesis가 없으면 링크를 숨긴다. 새 분석·저장 항목 열기·입력 채우기·사진 인식 시작·페이지 이탈 시 정지. 긴 문장은 80자 이하 조각으로 나눠 읽는다.
- 코드는 public/jgrammar.html 안에 있다(별도 JS 파일로 분리하지 않음: sw.js가 JS를 cache-first로 서빙해 수정이 반영되지 않을 수 있어서). 순수 함수 구간("<speech-pure>")을 tests/jgrammar_speech.test.js가 그대로 꺼내 시험한다.
- 앱에는 별도로 서버 음성 합성(routes/tts.js, OpenAI tts-1-hd, DB 캐시 tts_cache)이 있으며 언어 사전의 단어 발음용이다. 일본어 문법 읽어주기는 이를 쓰지 않는다. 음성 학습(voice_study.html)의 요약 읽어주기(작업182)와 같은 브라우저 내장 방식이지만 코드는 따로 만들었다.
